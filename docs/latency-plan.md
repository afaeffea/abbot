# План: сократить паузу бота в телефонном звонке

Статус на 2026-09-21. Прод: коммит `0e8d1b2`, Railway `abbot-production-2e99`.
Стек: STT Yandex SpeechKit, TTS Yandex (`alena`), LLM `gpt-5.6-luna`.

Документ для передачи работ. Каждый пункт: **что делать / зачем / сколько
это даёт / как проверить**. Порядок — по отношению выигрыш/риск, не по
удобству реализации.

---

## 0. Откуда цифры

В `0e8d1b2` в бэкенд добавлена поразрядная разбивка времени в stdout — она
переживает редеплой (в отличие от `call_logs/`, который лежит на эфемерном
диске Railway и стирается каждым пушем). Формат:

```
[timing:<call_id>] turn 0  vad=800 stt=481 llm=2548 tts=1222 -> silence=5051ms | reply=214ch tool=—
[timing:<call_id>] ==== call summary ====
[timing:<call_id>] llm=gpt-5.6-luna stt=yandex tts=yandex
[timing:<call_id>]   SILENCE total   med= 4972ms max= 5051ms n=2
```

Читать так:
```bash
curl -s https://backboard.railway.app/graphql/v2 \
  -H "Project-Access-Token: $RAILWAY_TOKEN" -H 'Content-Type: application/json' \
  -d '{"query":"{deploymentLogs(deploymentId:\"<id>\",limit:500,filter:\"timing\"){timestamp message}}"}'
```
(`urllib`/`requests` отдают 403 от Cloudflare — нужен именно `curl`.)

**Замер живого входящего звонка 2026-09-21 14:53** (`20260921-145328-bf2eb2`):

| стадия | ход 1 | ход 2 | медиана | доля |
|---|---|---|---|---|
| VAD hangover | 800 | 800 | 800 ms | 16% |
| STT (Yandex, финальный транскрипт) | 481 | 303 | 392 ms | 8% |
| **LLM (до первого токена)** | **2548** | **2945** | **2746 ms** | **55%** |
| TTS (до первого аудио-чанка) | 1222 | 846 | 1034 ms | 21% |
| **тишина в трубке (бэкенд)** | **5051** | **4894** | **4972 ms** | |

Плюс **~590 мс** между `tts_first_audio` в бэкенде и `outbound_media_started`
в VoxEngine (RTP-плечо, ресемпл, пейсер). Реально абонент молчит **≈5.6 с**.

**Главная находка.** Весь текст реплики долетает за 50–160 мс после первого
токена (в логах `43.018 → 43.178`). То есть 2.7 с — это *чистое ожидание
первого токена*, а не генерация. Из этого следует:

> Укорачивание реплик и пословная отдача в TTS **не дадут ничего**. Эти 2.7 с
> лечатся только сменой модели или тем, что запрос уходит раньше.

## 1. Стенд замера: правильная метрика и правильный хост

**Что делать.** Написать `scripts/bench_llm.py` и гонять его **не с рабочей
машины**, а с того же сетевого плеча, что прод (Railway-контейнер, либо
любой не-РФ хост).

**Зачем.** Два дефекта имеющихся замеров, из-за которых нельзя принять
решение по модели:

1. **Метрика не та.** Стенд, который уже есть (10 моделей × 16 задач,
   160 прогонов, все 16/16 корректны), меряет **полное время ответа**. Для
   голоса значение имеет **время до первого произносимого токена (TTFT)** —
   всё до него абонент слышит как тишину, а всё после уже перекрывается
   воспроизведением. У «думающих» моделей это разные величины на секунды:
   `z-ai/glm-5.3-fast` выдаёт **749 символов рассуждения** прежде первого
   слова ответа.
   Второй дефект того стенда: задачник **насыщен** — 10/10 моделей дали
   16/16. Он больше не различает модели по качеству, только по скорости.

2. **Хост не тот.** OpenAI с российского IP отдаёт
   `403 unsupported_country_region_territory` на любой запрос — ключ рабочий,
   блокируется страна. То есть локально кандидат `gpt-*` не измеряется в
   принципе, а замеры TokenRouter с локальной машины включают свой сетевой
   путь и несопоставимы с прод-цифрами.

**Требования к стенду** (не косметика, каждое закрывает уже наступившие грабли):
- реальная история из сохранённого транскрипта звонка + реальный системный
  промпт из `data/01_09/` (~5.9 тыс. символов) — на «привет» латентность
  другая;
- тот же единственный инструмент `qualify_lead`, что отдаёт телефонная сессия;
- **чередовать модели внутри повтора**, а не мерить блоками. В
  `llm_client.py:38-60` зафиксированы грабли: замер блоками дал «4.1-mini
  вдвое быстрее», что оказалось дрейфом нагрузки API. Интерливингом вышло
  1.02 с против 1.14 с — шум;
- отдельно писать `ttft` (первый *content*-дельта) и `first_any` (первый
  токен любого вида, включая рассуждение) — разница между ними и есть
  мёртвый эфир;
- считать долю корректных `qualify_lead` с валидными аргументами.

**Выигрыш.** Сам по себе нулевой, но без него пункты 2 и 3 — гадание.

## 2. Шов провайдера LLM + вердикт по GLM

**Что делать.** Ввести в `backend/llm_client.py` переменную `LLM_PROVIDER`
(`openai` | `tokenrouter`) по образцу уже существующего шва в `speech.py`
(там так же переключаются STT/TTS). Развилки, которые он обязан закрыть:

| | OpenAI | TokenRouter |
|---|---|---|
| `base_url` | дефолт SDK | `https://api.tokenrouter.com/v1` |
| лимит вывода | `max_completion_tokens` (gpt-5 отвергает `max_tokens`) | `max_tokens` |
| `reasoning_effort` | только gpt-5.*; gpt-4.1-* отвергают сам аргумент | не слать никогда |
| выключение thinking | — | `extra_body={"thinking":{"type":"disabled"}}` |

Логику не размазывать по вызовам: `completion_kwargs()` — единственное место,
которое знает про эти квирки (модель менялась уже пять раз, и каждый раз
ломалось именно то, что знало про модель на месте вызова).

**Зачем и какой вердикт по GLM.** Проверено прямыми запросами 2026-09-21
(системный промпт-заглушка, `max_tokens=200`, TokenRouter):

| модель | thinking off | стриминг | TTFT / время |
|---|---|---|---|
| `z-ai/glm-5.3-fast` | **400: «GLM-5.3 does not support disabling thinking»** | зависает >90 с | sync 3.09 с, 749 симв. рассуждения |
| `z-ai/glm-5-turbo` | да (`think=0`) | да | **TTFT 10.3 с** |
| `z-ai/glm-4.6` | да (`think=0`) | да | **TTFT 7.0 с** |
| `mistral/mistral-small-2603` | — | — | `503 model_not_found` |
| `deepseek/deepseek-v4.1` | — | — | `503 model_not_found` |

То есть **на сегодня GLM через TokenRouter — не кандидат в прод**: у лучшего
из отвечающих TTFT втрое хуже текущих 2.7 с, у самого быстрого (`5.3-fast`,
1.51 с у прошлого стенда) не работает стриминг и не выключается рассуждение.
Плюс роутер держит ~9 rpm, чего не хватит на кампанию.

**Но шов всё равно нужен**, и это не противоречие: цифры выше сняты с
заблокированной машины, часть моделей роутера в тот момент лежала (`503`), а
единственный способ перепроверить это на прод-плече — иметь возможность
переключить провайдера переменной окружения, без правки кода и редеплоя
логики. Шов стоит ~40 строк и делает пункт 1 исполнимым на живом стенде.

**Выигрыш.** Прямого нет. Открывает возможность увести 2.7 с, которые
составляют 55% паузы, — сейчас такой возможности нет вообще.

## 3. Сменить модель по результатам замера

**Что делать.** Прогнать стенд из п.1 на прод-плече и выбрать по TTFT среди
тех, кто проходит по надёжности.

**Зачем.** Текущая `gpt-5.6-luna` плоха дважды:
- **2.7 с до первого токена** — больше половины паузы;
- **надёжность вердикта**. На 24-диалоговом прогоне (2026-09-02,
  `llm_client.py:38-60`): `gpt-4.1-mini` — 23/24 корректных вердикта,
  `gpt-5.6-luna` — **12/24**, то есть в половине звонков молча не зовёт
  `qualify_lead`. Костыль `FORCE_QUALIFY_AFTER_TURNS = 6` существует именно
  ради этого.

Заметь: дефолт в коде — `gpt-4.1-mini`, а `gpt-5.6-luna` приходит переменной
окружения `LLM_MODEL` на Railway. Откат — правка одной переменной, редеплой
кода не нужен.

**Осторожно.** Не выбирать по латентности без интерливинга (см. п.1) и не
переносить сюда цифры «полного времени ответа» из старого стенда.

**Выигрыш.** До ~1.5 с из 5.6 с, если найдётся модель с TTFT ~1.2 с.
Плюс возврат корректного вердикта в ~11 звонках из 24 — это уже не
латентность, а деньги кампании.

## 4. Запускать LLM на промежуточном транскрипте

**Что делать.** В `telephony_session.py`, в VAD-цикле по `event.speech_end`,
сейчас идёт `recorder.mark_speech_end()` → `await stt.end_utterance()` →
ожидание финального транскрипта → только потом запрос в LLM. Отправлять
запрос на последнем *партиальном* транскрипте, а финальный использовать для
отмены/перезапуска, если он разошёлся с партиалом (механика отмены уже есть —
это `context_id` и обработка barge-in).

**Зачем.** STT-плечо в замере — 303–481 мс, и всё это время модель не знает
ни слова из того, что уже распознано.

**Выигрыш.** ~300–480 мс, измерено. Риск: лишний запрос к LLM, когда
финальный транскрипт разошёлся с партиалом (деньги, не качество).

## 5. Разобраться с ~590 мс между бэкендом и VoxEngine

**Что делать.** Сопоставить `tts_first_audio` из `[timing:...]` с
`outbound_media_started` в логах VoxEngine на одном и том же звонке и найти,
где именно они уходят: ресемпл 24k→8k, μ-law, буфер пейсера, RTP-плечо.

**Зачем.** Эти 590 мс **не измерялись никогда** — все цифры в таблице
кончаются на моменте, когда аудио готово в бэкенде. Абонент ждёт больше, чем
показывает любой наш лог.

**Выигрыш.** Неизвестен до вскрытия — это единственный пункт, где нельзя
назвать число. Потолок 590 мс, реалистично часть из них — неустранимое RTP.
Делать после п.3-4, но не откладывать: непромеренный участок в 10% паузы.

## 6. VAD hangover 800 → ~550 мс

**Что делать.** `TELEPHONY_SILENCE_HANGOVER_MS` в `telephony_session.py:168`.

**Зачем.** Это фиксированное ожидание тишины перед тем, как бот вообще
считает, что абонент договорил. 800 мс — 16% паузы, и они платятся **каждый
ход**.

**Выигрыш.** 250 мс, детерминированно, правка одной константы.
**Риск реальный:** слишком короткий hangover режет абонента на паузе в
середине фразы, и это хуже медленного бота. Менять только вместе с
прослушиванием записей 5–10 живых звонков, не «на глаз».

## 7. TTS: первое предложение отдельно

**Что делать.** Yandex синтезирует флашнутое предложение целиком, стримингом
не отдаёт — отсюда 846–1222 мс. Варианты: синтезировать первое предложение
отдельным коротким запросом, пока готовится остальное; либо вернуть Cartesia
на первый чанк (интеграция уже написана, `cartesia_realtime.py`).

**Зачем.** 1.0 с — 21% паузы, второе место после модели.

**Выигрыш.** Ориентировочно 400–700 мс на первом чанке. Не измерено —
требует прототипа.

## 8. Входящие звонки получают исходящий скрипт (корректность, не скорость)

**Что делать.** `inbound.voxengine.js` зовёт `createTelephonyBridge(call)`
**без аргументов**, `outbound.voxengine.js` — с номером и именем. Бэкенд
поэтому не знает направления звонка (в логе видно `phone=— name=—`) и
читает тот же единственный `settings_override.json`, куда
`apply_event_settings.py` кладёт настройки кампании.

Пробросить из inbound-сценария признак направления и дать входящим свой
набор настроек и инструментов.

**Зачем.** Прямо сейчас человек, позвонивший на +7 495 108-42-40, получает
исходящий питч турнира 1 сентября, вызов `qualify_lead` и сброс на 29-й
секунде. Это воспроизведено на живом звонке 2026-09-21.

**Выигрыш.** Латентности не даёт. Чинит поведение, которое видит каждый
входящий клиент.

## 9. Прочее, что нашлось по дороге

- **Открытые эндпоинты.** Без авторизации доступны `/api/calls`,
  `/api/calls/{id}/audio` (записи разговоров с клиентами),
  `/api/settings` GET и PUT, `/api/settings/reset`, `/api/voices`,
  `/api/settings/test-chat`. Токен (`X-Telephony-Token`) стоит только на
  `/api/telephony/*`. PUT настроек без авторизации — это возможность переписать
  промпт бота снаружи; логи показывают, что эндпоинты сканируют.
- **Эфемерный диск.** `settings_override.json` и `call_logs/` умирают на
  каждом редеплое, а любой пуш — редеплой. После каждого деплоя обязательно:
  `python3 scripts/apply_event_settings.py data/01_09 --backend-url https://abbot-production-2e99.up.railway.app`.
  Записи звонков при этом восстановить нельзя. Нужен внешний том или S3.
- **Мёртвая переменная `OPENAI_MODEL=gpt-4.1-mini`** на Railway — её не
  читает ни строчки кода с коммита `9304db5`. Удалить, пока её не покрутили
  вместо `LLM_MODEL`.
- **`CARTESIA_VOICE_ID`** на Railway (`25b7aaa6-…`) и локально
  (`1e4176b1-…`) разные. Пока `TTS_PROVIDER=yandex` — неважно, выстрелит при
  возврате Cartesia (п.7).
- **Бонусы из `data/01_09/offer.txt`** (доп. билет в розыгрыш за раннюю
  регистрацию, билет за друга, стикеры и браслет первым 30) не упомянуты
  ни в промпте, ни в фактах — бот физически не может ими продавать.
