# Warpoint — голосовой ИИ-администратор (потоковый звонок STT → LLM → TTS)

Голосовой ИИ-администратор, который ощущается как настоящий телефонный звонок: браузер непрерывно стримит голос по WebSocket → **Cartesia STT (Ink-Whisper, realtime WS)** распознаёт речь на лету → **OpenAI (`gpt-5.6-luna`, Chat Completions API, streaming)** генерирует ответ администратора парка токен за токеном → **Cartesia TTS (Sonic, realtime WS)** озвучивает ответ по мере генерации текста → браузер проигрывает аудио потоково, без ожидания полного файла. Все вызовы к API — настоящие, без моков. Бот сам здоровается первым, как только звонок начинается — фиксированной фразой напрямую в озвучку, без обращения к модели (см. «Настройки бота» ниже).

Настоящие телефонные звонки (через Voximplant, входящие и исходящие) тоже поддерживаются — см. «Телефония (Voximplant)» ниже. Настоящая база данных для броней **пока не подключена** — это следующий этап (см. «Что дальше» внизу). История диалога во время звонка хранится только в памяти процесса (сбрасывается по завершении звонка); после звонка остаётся запись + транскрипт на диске (см. «Логи звонков» ниже), а не структурированная база.

## 1. Настройка окружения

```bash
cd backend
cp .env.example .env
```

Откройте `backend/.env` и впишите:
- `CARTESIA_API_KEY` — ключ из [Cartesia](https://play.cartesia.ai/) (Settings → API Keys).
- `OPENAI_API_KEY` — ключ из [platform.openai.com](https://platform.openai.com/api-keys). Модель — `LLM_MODEL` (по умолчанию `gpt-5.6-luna`); переопределять `base_url` не нужно, SDK по умолчанию стучится в сам OpenAI.

`CARTESIA_VOICE_ID` можно оставить пустым — сервер сам подберёт первый доступный голос для языка `CARTESIA_LANGUAGE` (по умолчанию `ru`) через реальный запрос к Cartesia `GET /voices`. Если хотите конкретный голос — выберите его в [библиотеке голосов Cartesia](https://play.cartesia.ai/voices) и впишите его ID в `CARTESIA_VOICE_ID`.

## 2. Установка и запуск

```bash
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
cd backend
uvicorn main:app --reload --port 8000
```

(`requirements.txt` лежит в корне репозитория, а не в `backend/` — это важно для деплоя на Railway, см. ниже.)

## 3. Открыть сайт

http://localhost:8000

Нажмите «Начать», разрешите доступ к микрофону — бот сразу поздоровается голосом. С этого момента и до конца разговора работает настоящий гибрид, без переключения режимов и без кнопок «микрофон вкл/выкл»:
- **Голосом** — микрофон слушает непрерывно весь звонок, как в настоящем телефонном разговоре. Бот сам определяет паузы в речи (voice activity detection) и отвечает без необходимости нажимать что-либо между репликами.
- **Текстом** — поле ввода внизу доступно всегда, параллельно с микрофоном; напишите реплику и нажмите «Отправить» — ответ придёт **и текстом, и голосом** через тот же гапless TTS-плеер.

Оба канала совмещены: можно в любой момент либо начать говорить, либо написать — что бы ни случилось раньше, это и есть перебивание (barge-in), сервер отменяет текущий ход диалога и сразу начинает обрабатывать новый ввод (см. barge-in ниже). Если доступ к микрофону не дан или недоступен, звонок всё равно продолжается — просто без голосового канала, чисто текстом. Чат-бокс показывает вживую: статусные строки, промежуточный (частичный) и финальный распознанный текст, ответ модели по мере генерации. «Завершить» останавливает микрофон и закрывает соединение.

### Если что-то идёт не так
- **Бот не слышит / не реагирует на паузы** — микрофон может быть слишком тихим или слишком шумным для порога VAD («Порог энергии (обычный)» на странице настроек `/prompt.html`, по умолчанию `0.02`). Увеличьте порог для шумного помещения, уменьшите для тихого микрофона.
- **Бот перебивает слишком быстро/долго ждёт** — поменяйте «Тишина до конца реплики» (по умолчанию 700 мс — сколько тишины нужно, чтобы решить, что собеседник договорил; это главный рычаг воспринимаемой задержки ответа) на странице настроек.
- **Бот обрывает сам себя / в реплике пользователя появляется бессмысленный повторяющийся текст** — это акустическая обратная связь: без наушников колонки проигрывают голос бота, микрофон улавливает этот же звук и распознаёт его как попытку перебить. Пока бот говорит, порог перебивания немного строже обычного («Порог энергии при перебивании» / «Задержка перебивания», по умолчанию `0.035`/`250` мс), плюс включено эхоподавление браузера (`echoCancellation`) — если всё равно происходит, используйте наушники или увеличьте оба значения.
- **Не получается перебить бота голосом (перебивание текстом при этом работает)** — обратный случай: порог перебивания слишком строгий для вашего микрофона/громкости голоса. Уменьшите оба значения на странице настроек.
- Любая ошибка от Cartesia/модели выводится в чат-боксе как есть (красным) — конвейер не глотает ошибки.

## Как это устроено технически (коротко)

- Один WebSocket `/ws/call` на весь звонок: аудио от микрофона идёт бинарными фреймами, статусы/транскрипты/текст ответа — JSON-сообщениями, аудио бота — бинарными фреймами обратно.
- `mic-worklet.js` берёт сырой звук с микрофона на audio-потоке рендеринга, ресемплирует до 16kHz PCM16 (формат Cartesia STT) и детектит паузы в речи (VAD) без участия сервера.
- Как только VAD фиксирует конец фразы, фронтенд посылает `end_of_utterance`, backend отправляет Cartesia STT команду `finalize`, получает финальный транскрипт и запускает ход диалога.
- Ответ модели стримится по токенам; как только накопилось законченное предложение, оно сразу уходит в Cartesia TTS (потоковый контекст с `continue: true`/`false`) — бот начинает говорить, не дожидаясь конца всего ответа.
- Аудио от TTS приходит чанками и проигрывается через Web Audio API с точным планированием времени старта каждого чанка (гапless-очередь), а не через `<audio>.play()` — это одновременно даёт низкую задержку и обходит блокировку автовоспроизведения браузером, так как `AudioContext` создаётся синхронно по клику на кнопку «Начать звонок».

## Перебивание бота (barge-in)

Можно перебить бота голосом прямо во время его речи — как только VAD улавливает начало вашей реплики, фронтенд мгновенно останавливает воспроизведение и шлёт `interrupt` на бэкенд, который отменяет текущий ход диалога (OpenAI-стрим и TTS-контекст) и сразу начинает слушать новую реплику. Старое, уже отменённое аудио от TTS отбрасывается по `context_id`, чтобы не проигралось поверх нового ответа.

То же самое работает и текстом: отправка сообщения, пока бот ещё говорит, точно так же отменяет текущий ход и запускает новый — отдельно жать что-то для «прерывания» не нужно, само сообщение и есть прерывание.

## Настройки бота

Страница **`/prompt.html`** (ссылка есть на главной и в логах звонков) — панель тонкой настройки бота без правки кода и без редеплоя. Изменения применяются к **новым** звонкам сразу после сохранения; уже идущий в этот момент разговор продолжает использовать те настройки, с которыми начался. Страница без пароля, как и весь остальной сайт сейчас.

Что можно настроить:
- **Приветствие** — первая фраза бота при старте звонка. Отправляется напрямую в озвучку, **минуя модель полностью** — не LLM-вызов, а фиксированный текст. Раньше приветствие генерировала модель по скрытой команде, и это регулярно оказывалось самым нестабильным ходом диалога (модель могла уйти в несвязанный текст на первых секундах звонка — именно там это особенно заметно и неприятно). Теперь это невозможно в принципе: нет вызова модели — нет риска галлюцинации.
- **Персона и поведение** — кто бот, стиль речи, правила вызова функции бронирования. Отдельное поле от бизнес-фактов специально, чтобы правка цены не могла случайно сломать инструкции по поведению.
- **Бизнес-факты** — адрес, цены, тарифы, состав пакетов. То, что меняется чаще всего.
- **Параметры модели** — `reasoning_effort` (сейчас **не влияет ни на один реальный звонок**: `gpt-5.6-luna` требует ровно `"none"` при использовании функций, а функции доступны в каждом ходе, так что `backend/llm_client.py::completion_kwargs` молча подставляет `"none"` вместо выбранного здесь значения — поле оставлено рабочим на случай будущей модели без этого ограничения), `temperature` (по умолчанию не задан — используется значение провайдера), голос Cartesia (по умолчанию — автовыбор первого доступного для `CARTESIA_LANGUAGE`, есть выпадающий список реальных голосов), максимум токенов на ответ `max_reply_tokens` (по умолчанию 400, диапазон 50–2000 — слишком маленькое значение рискует обрезать фразу или помешать вызову `confirm_booking`).
- **Чувствительность микрофона** — те же VAD-пороги, что раньше были зашиты в `frontend/app.js` (`energyThreshold`, `speechStartMs`, `silenceHangoverMs`, `bargeInEnergyThreshold`, `bargeInSpeechStartMs`), теперь редактируются на странице; фронтенд запрашивает актуальные значения при каждом новом звонке (не кэширует на весь просмотр страницы), с тихим откатом на дефолты при любой ошибке запроса.
- **Тестовый чат** — прямо на странице настроек, проверяет **черновые** (ещё не сохранённые) значения всех полей выше, до того как они уйдут в реальные звонки. Многоходовый (можно проверить полный сценарий брони), только текстом, без синтеза речи. Показывает, если сработала функция `confirm_booking`, и явно предупреждает, если ответ модели пришлось обрезать из-за похожего на код/JSON текста — то самое, от чего боевой конвейер защищает молча.

Кнопка «Восстановить по умолчанию» откатывает все поля к исходным значениям из `backend/settings_defaults.py`. Настройки хранятся в `backend/settings_override.json` — как и `backend/call_logs/`, это runtime-состояние на диске, а не часть кода: переживает рестарты в рамках одного деплоя на Railway, но исчезает при следующем передеплое (после которого бот снова стартует с настройками по умолчанию).

## Логи звонков и бронирование (tool-calling)

Когда собеседник подтверждает все детали брони (услуга, дата, время, количество человек), модель по-настоящему вызывает функцию `confirm_booking(...)` (реальный OpenAI tool-calling, а не просто текст) — это даёт структурированный «итог звонка», а не только устную фразу.

Каждый разговор пишется на диск в `backend/call_logs/<call_id>/`:
- `recording.wav` — стерео-запись (пользователь слева, бот справа), собранная из реального аудио звонка; для ходов, отправленных текстом, дорожка пользователя в этом промежутке остаётся тихой, так как речи не было;
- `transcript.json` — по каждому ходу: распознанный/введённый текст, ответ бота, задержка до первого токена LLM и до первого байта озвучки (от момента окончания речи/отправки сообщения), вызванные функции, был ли ход прерван перебиванием.

Окно просмотра — **`/logs.html`** (ссылка есть на главной странице): список звонков с итогом брони, при клике — плеер записи и таблица ходов с задержками. Доступ пока без защиты (см. ниже про Railway — эфемерная ФС).

**Важно:** файловая система на Railway для этого сервиса эфемерна без подключённого Volume — записи и логи переживут рестарты в рамках одного деплоя, но исчезнут при следующем деплое. Для долгосрочного архива нужен Railway Volume (настраивается в дашборде) либо лог в Google Таблицу ниже — таблица переживёт передеплой в любом случае.

## Лог в Google Таблицу

Опциональная фича: после каждого завершённого разговора (звонка) в указанную Google Таблицу дописывается строка с итогом — время начала, длительность, была ли бронь (и её детали), `call_id`, количество ходов диалога. В отличие от `backend/call_logs/`, таблица не зависит от эфемерной ФС Railway и переживает передеплой.

Без настройки фича молча выключена — сервер работает как обычно, просто без записи в таблицу. Чтобы включить, настройте с нуля:

1. Откройте [Google Cloud Console](https://console.cloud.google.com/) и создайте новый проект (или выберите существующий).
2. В библиотеке API включите **Google Sheets API** для этого проекта (Google Drive API включать не нужно — таблица открывается по ID через `open_by_key`, а не по имени/поиску).
3. Перейдите в **IAM & Admin → Service Accounts**, создайте новый сервисный аккаунт (роль можно не назначать — доступ к конкретной таблице выдаётся отдельно, см. шаг 6). Откройте созданный аккаунт → вкладка **Keys** → **Add Key → Create new key → JSON** — скачается файл ключа.
4. Откройте скачанный JSON-файл и вставьте **всё его содержимое целиком** (это валидный JSON-объект) как значение `GOOGLE_SERVICE_ACCOUNT_JSON` в `backend/.env` (или в Variables на Railway).
5. Создайте Google Таблицу (или возьмите существующую) — первый лист (`sheet1`) будет использоваться для записи. Скопируйте ID таблицы из её URL: `https://docs.google.com/spreadsheets/d/`**`ID_ТАБЛИЦЫ`**`/edit` — впишите его в `GOOGLE_SHEETS_SPREADSHEET_ID`.
6. Откройте доступ к таблице для сервисного аккаунта: кнопка «Настройки доступа» в таблице → добавить `client_email` из JSON-ключа (строка вида `...@...iam.gserviceaccount.com`) с ролью **Редактор** — так же, как обычного пользователя.
7. Перезапустите/передеплойте сервер. Если переменные не заданы — фича просто не активируется, без ошибок в логе; при ошибке авторизации/доступа (например, забыли шаг 6) в логе сервера будет предупреждение `[sheets_logger] ...`, но сам разговор при этом не ломается.

## Телефония (Voximplant)

Настоящие телефонные звонки — входящие на арендованный номер и исходящие (бот сам звонит) — работают через [Voximplant](https://voximplant.com/): их сторона исполняет JS-сценарий (VoxEngine) в своём облаке, который открывает WebSocket к нашему бэкенду (`/ws/telephony`) и стримит туда аудио звонка (кодек G.711 μ-law, 8kHz — стандарт телефонии). Направление «звонящий → бэкенд» идёт через этот WebSocket (`call.sendMediaTo(ws)`) в общий конвейер Cartesia STT → LLM, тот же самый, что у браузерного звонка (`backend/session_base.py` общий для обоих транспортов); вместо `mic-worklet.js` паузы в речи ловит серверный VAD (`backend/telephony_vad.py`, те же настройки чувствительности, что на странице `/prompt.html`).

**Направление «бот → звонящий» несимметрично входящему, и это главная ловушка этого файла.** Голос бота синтезирует сам бэкенд (тот же Cartesia, что и в браузере), после чего отправляет его в тот же WebSocket — но не сырыми байтами, а в формате `Voximplant.WebSocketFormat`: сначала `StartEvent` с названием кодека, затем по одному JSON-событию `media` на каждые 20 мс звука, с base64-полем `payload` и **обязательными** `chunk` и `timestamp` ([формат](https://voximplant.com/docs/guides/media-streams/format), [схема](https://github.com/voximplant/protobuf/blob/main/websockets.proto)). Сценарий подключает этот поток в звонок через `ws.sendMediaTo(call)`.

То есть VoxEngine отдаёт нам голос звонящего сырыми бинарными кадрами, но принимать в обратную сторону согласен только эти JSON-события. Предположение о симметричности сокета — причина, по которой пять предыдущих попыток проваливались одинаково: кадры уходили без ошибок, сокет оставался открытым, звонящий не слышал ничего. Единственное положительное подтверждение, что поток вообще принят, — событие `WebSocketEvents.MEDIA_STARTED` в сценарии; оно приходит только если `StartEvent` корректен, и сценарий пересылает его в бэкенд как диагностику.

Из той же спецификации следуют ещё две вещи. Voximplant буферизует присланное и сам воспроизводит в реальном времени, но **буфер ограничен 10 секундами, лишнее молча выбрасывается** — поэтому `_pace_outbound_audio` в `backend/telephony_session.py` держит запас около 1.5 секунды, а не шлёт всё разом. И при перебивании нужно очищать именно этот буфер (`ws.clearMediaBuffer()`), иначе бот продолжит говорить поверх звонящего ещё несколько секунд.

Голос бота попадает в запись звонка напрямую: бэкенд сам синтезировал эти байты, поэтому пишет их через `recorder.record_tts_chunk()` — так же, как на браузерном транспорте. Отдельный WebSocket для записи, который был нужен в старой схеме (когда синтез жил на стороне Voximplant), больше не используется.

### Настройка (один раз, в панели Voximplant)

1. **Control Panel → Applications** — создать приложение.
2. **Внутри приложения → Scenarios** — создать два пустых сценария (один для входящих, один для исходящих) и запомнить их ID. Дальше содержимое в них заливает `scripts/deploy_voximplant.py` (см. ниже) — вручную копировать код в редактор не нужно и не стоит.
3. **Routing rule для входящих** — привязать к арендованному номеру (шаг 4) и к сценарию с `inbound.voxengine.js`.
4. **Numbers** — арендовать номер (российский, раз бот говорит по-русски), привязать к приложению.
5. **Routing rule для исходящих** — без паттерна номера, привязать к сценарию с `outbound.voxengine.js`. Он запускается только через API (шаг 7), не автоматически.
6. **Settings/API** — получить `account_id` и `api_key`.
7. Заполнить в `backend/.env`: `VOXIMPLANT_ACCOUNT_ID`, `VOXIMPLANT_API_KEY` (шаг 6), `VOXIMPLANT_OUTBOUND_RULE_ID` (ID правила из шага 5), `VOXIMPLANT_CALLER_ID` (номер из шага 4), `TELEPHONY_WS_TOKEN` (общий секрет с бэкендом), `VOXIMPLANT_OUTBOUND_SCENARIO_ID` и `VOXIMPLANT_INBOUND_SCENARIO_ID` (шаг 2), `RAILWAY_PUBLIC_DOMAIN`.
8. Залить код сценариев:

```bash
python scripts/deploy_voximplant.py --dry-run   # собрать и проверить, ничего не заливая
python scripts/deploy_voximplant.py             # залить оба сценария
```

Скрипт подставляет домен, токен и номер из `backend/.env` и **отказывается заливать сценарий, в котором осталась заглушка**. Это не формальность: если оставить `CALLER_ID` равным `+70000000000`, каждый исходящий звонок падает с голым «403 Forbidden» от оператора, и в логах бэкенда об этом не будет ни строчки. Повторять этот скрипт нужно после **любого** изменения файлов в `voximplant/` — код в панели Voximplant не обновляется сам по `git push`.

### Как позвонить самому боту (исходящий звонок)

```bash
curl -X POST https://<ваш-домен>/api/telephony/call \
  -H "X-Telephony-Token: <TELEPHONY_WS_TOKEN>" \
  -H "Content-Type: application/json" \
  -d '{"phone_number": "+79991234567"}'
```

Это реальный, платный звонок — эндпоинт защищён токеном специально (единственное защищённое место во всём приложении, см. комментарий в `main.py`), в отличие от остального сайта.

### Обзвон по базе контактов из Excel (основной сценарий)

`scripts/run_campaign.py` берёт выгрузку контактов, обзванивает их через уже задеплоенный бэкенд и складывает результат рядом с исходным файлом. Именно этим запускается кампания — страница `/campaign.html` ниже осталась от ручной вставки списка номеров.

**Порядок запуска, по шагам:**

```bash
# 0. Один раз: зависимости и секреты
pip install -r scripts/requirements.txt
cp backend/.env.example backend/.env   # и заполнить (ключи спросить у владельца проекта)

# 1. Проверить, что LLM отвечает (см. блок про риск ниже -- это самая частая причина сорванной кампании)
curl -s https://api.openai.com/v1/chat/completions \
  -H "Authorization: Bearer $OPENAI_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"gpt-5.6-luna","messages":[{"role":"user","content":"привет"}],"max_completion_tokens":5}'

# 2. Сценарии в Voximplant соответствуют коду (после любых правок в voximplant/)
python scripts/deploy_voximplant.py

# 3. Переключить бота на нужное мероприятие. ОБЯЗАТЕЛЬНО перед каждым обзвоном:
#    Railway стирает настройки при каждом редеплое (см. ниже).
python scripts/apply_event_settings.py data/01_09 \
    --backend-url https://<ваш-домен>

# 4. Контрольный звонок СЕБЕ -- убедиться, что бот жив и говорит про нужное событие
curl -X POST https://<ваш-домен>/api/telephony/call \
    -H "X-Telephony-Token: <TELEPHONY_WS_TOKEN>" \
    -H "Content-Type: application/json" \
    -d '{"phone_number": "+79991234567"}'

# 5. Пилот на 10-20 контактах. --limit ОБЯЗАТЕЛЕН: в боевой выгрузке несколько
#    тысяч строк, без него скрипт начнёт обзванивать их все.
python scripts/run_campaign.py data/01_09/CONTACT_*.xls \
    --backend-url https://<ваш-домен> \
    --token "$TELEPHONY_WS_TOKEN" \
    --concurrency 2 \
    --limit 20 \
    --label "01_09-pilot"

# 6. Посмотреть выгрузку результатов, и только потом снимать --limit
```

**Что получится на выходе.** Рядом с исходной выгрузкой ляжет `<имя_файла>_результаты_<прогон>.xlsx`: все исходные колонки плюс `квалификация` (готов / отказ / не определился), `итог разговора`, `дозвон`, `длительность`, `реплик`, `время звонка` и `call_id`. Исходный файл не меняется — это выгрузка из CRM, следующий экспорт всё равно её перезапишет. Полные расшифровки и сырые строки — в `scripts/campaign_runs/<прогон>/`.

**Три правила, нарушение которых стоит данных или денег:**

- **Не делать `git push` и не редеплоить бэкенд, пока идёт обзвон.** Настройки мероприятия и история звонков живут на эфемерном диске и в памяти процесса — редеплой посреди кампании и сбросит бота на дефолтный промпт, и потеряет вердикты по звонкам, которые скрипт ещё не успел забрать.
- **`--concurrency` ограничена не LLM, а Cartesia.** Один звонок тратит 3–5 запросов к модели — на OpenAI это с большим запасом выдержит десятки параллельных звонков (точный лимит запросов/мин для вашего аккаунта не проверен, посмотрите его на [platform.openai.com/settings/organization/limits](https://platform.openai.com/settings/organization/limits) перед крупной кампанией). Реальный потолок — тариф Cartesia (TTS-коннектор Voximplant), см. подсказку на `/campaign.html`.
- **Сначала пилот на 10–30 контактах (`--limit`), потом весь список.** Дешевле найти проблему на двадцати живых людях, чем на нескольких тысячах. Отдельно: конвейер `run_campaign` целиком (параллельность, склейка результатов, запись xlsx) вживую на реальной кампании ещё не гонялся — первый пилот и есть его проверка, а не формальность.

**Что смотреть после пилота, прежде чем снимать `--limit`:**

- В выгруженном xlsx у дозвонившихся заполнены `квалификация` и `итог разговора` — если пусто, вердикты не собираются, и продолжать бессмысленно.
- В `scripts/campaign_runs/<прогон>/results.jsonl` доля `dial_status: "dialed"` — много `timeout` означает, что звонки не укладываются в `--timeout` или упёрлись в лимит роутера.
- Послушать 2–3 записи разговоров целиком (`scripts/campaign_runs/<прогон>/transcripts/`): не оборвался ли бот на полуслове, адекватны ли ответы.

**Риск: LLM-провайдер может отвалиться посреди кампании.** Модель вызывается напрямую у OpenAI, и отказать всё ещё может: `401`/`403` — ключ или биллинг, `429` — упёрлись в лимит запросов/квоту, `5xx` — сторона OpenAI недоступна. Раньше (на прямом Gemini) это было частым и тяжёлым — модель то и дело уходила в `503 high demand` на десятки минут без предупреждения и без официально признанного инцидента; именно это и стало причиной перехода на OpenAI.

Бот это переживает, но не бесплатно: запрос ограничен 8 секундами и двумя повторами, после чего он извиняется («связь подвисла») и просит повторить — то есть звонящий слышит живого собеседника, а не тишину, но разговор всё равно портится. Если такое пошло подряд, обзвон надо **останавливать**, а не досматривать: каждый звонок платный, а лид сгорает.

Как проверить перед запуском и по ходу:

```bash
# жива ли модель прямо сейчас
curl -s https://api.openai.com/v1/chat/completions \
  -H "Authorization: Bearer $OPENAI_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"gpt-5.6-luna","messages":[{"role":"user","content":"привет"}],"max_completion_tokens":5}'
```

Ответ с текстом — всё в порядке. Ошибка про неизвестную модель — версию сняли с раздачи, тогда менять `LLM_MODEL`, но **обязательно проверив на замену, что она вызывает `qualify_lead`** на достаточно большой выборке — **6 попыток недостаточно**: первая проверка `gpt-5.6-terra` на 6 попытках показала 6 из 6, но на 12 попытках просела до 7 из 12, тогда как `gpt-5.6-luna` на тех же 12 попытках дала 12 из 12 и вдобавок дешевле — поэтому сейчас в проде именно luna, а не более дорогая terra. Без этой перепроверки кампания молча перестанет собирать вердикты. Отдельно от надёжности исполнения: живые A/B-тесты (2026-08-30) на реальном `persona_prompt` показали, что **ни одна протестированная модель** (ни OpenAI, ни ранее Gemini) не распознаёт расплывчатые концовки («ну ладно, посмотрим» и похожие) надёжно — это системная граница, а не то, что чинится выбором модели. Отсюда предохранитель ниже.

Если у семейства `gpt-5.6-*` (`luna`/`terra`/`sol`) поменяется поведение API — два эмпирически найденных требования (`max_completion_tokens` вместо `max_tokens`, и `reasoning_effort` строго `"none"` при использовании функций) инкапсулированы в одном месте, `backend/llm_client.py::completion_kwargs()` — там и чинить, не в трёх местах вызова.

**Предохранитель на случай, если модель сама не завершает разговор.** `backend/telephony_session.py` считает ходы диалога с момента начала звонка (или последнего сброса счётчика); если `FORCE_QUALIFY_AFTER_TURNS` (сейчас 6) ходов прошло, а `qualify_lead` так и не прозвучал — бэкенд сам принудительно выводит вердикт из расшифровки разговора (тот же механизм, что уже был для случая, когда звонок оборвался вообще без вердикта, только теперь ещё и внутри живого звонка) и вешает трубку с общей прощальной фразой. Это грубый, а не хирургический механизм — специально не пытается угадывать по тексту, закончился ли разговор, просто ограничивает, сколько ходов подряд может пройти без результата.

В логах Railway признаки провала LLM: строки `turn failed -- apologising to the caller` и `gpt-5.6-luna: ...` (или другое имя модели) с кодом ошибки; признак срабатывания предохранителя — `LLM turns without qualify_lead -- forcing a mid-call verdict`.

### Обзвон вставленным списком номеров (ручной режим)

Страница `/campaign.html` — вставить список номеров (по одному на строку, E.164), задать паузу между звонками и нажать «Начать обзвон». Токен (`TELEPHONY_WS_TOKEN`) вводится там же и сохраняется в `localStorage` браузера, чтобы не вводить каждый раз. Звонки идут строго по очереди (не все разом) через `backend/telephony_campaign.py`: одно упавшее число (например, недоступный номер) не останавливает весь список — ошибка просто помечается в прогрессе, обзвон продолжается со следующего. Одновременно может идти только один обзвон; прогресс живёт в памяти процесса, не переживает рестарт/редеплой. Ограничение — 200 номеров за один запуск (`main.py`, `MAX_CAMPAIGN_NUMBERS`), это просто защита от случайной вставки огромного списка, а не реальный лимит.

## Деплой на Railway

В репозитории есть `Dockerfile` в корне — Railway обнаруживает его автоматически и использует вместо автоопределения (Railpack), так что структура `backend/` + `frontend/` собирается предсказуемо в один образ. Из настроек Railway нужно только:
- **Variables**: `CARTESIA_API_KEY`, `OPENAI_API_KEY` (обязательны; `LLM_MODEL` опционально, по умолчанию `gpt-5.6-luna`); для телефонии — `TELEPHONY_WS_TOKEN`, `VOXIMPLANT_ACCOUNT_ID`, `VOXIMPLANT_API_KEY`, `VOXIMPLANT_OUTBOUND_RULE_ID`, `VOXIMPLANT_CALLER_ID`; по желанию `GOOGLE_SHEETS_SPREADSHEET_ID`/`GOOGLE_SERVICE_ACCOUNT_JSON` для лога в Google Таблицу (см. выше) — `.env` в репозиторий не входит.
- **Root Directory**: оставить пустым (корень репозитория, где лежит `Dockerfile`).
